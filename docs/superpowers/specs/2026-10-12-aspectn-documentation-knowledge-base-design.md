# AspectN 使用文档与 Agent 知识库最终设计

- 日期：2026-10-12
- 状态：最终设计；五主题试点已实施，扩展与完整全仓闸门进度见[试点审查记录](../../reviews/2026-10-12-documentation-pilot.md)
- 范围：用户文档、Agent 知识库、能力证据、审查记录及同步检查
- 历史依据：[设计讨论稿及维护者裁决](../../../DOCUMENTATION-KNOWLEDGE-BASE-DESIGN.md)
- 配套材料：[字段格式与真实样例](2026-10-12-aspectn-documentation-knowledge-base-examples.md)

本设计整合讨论稿 §17 的 D1–D4、已经修订的正文及本会话的最终优化要求。它规定文档和工程流程，不改变现有 AspectN 语言、公共 API 或适配器行为。产品语义仍由既有正式规范及后续明确批准的修订决定。历史讨论中被本设计收敛或取代的流程建议不再作为实施依据。

## 1. 目标、范围与完成定义

系统提供两种阅读视图，共享同一套规范依据：

1. 用户文档按任务组织，帮助使用者选择适配器、编写表达式、处理结果和诊断、理解限制与常见坑。
2. Agent 知识库按 .NET/C# 功能及横向契约组织，回答能力承诺、适用条件、实现入口、证据和未验证边界。
3. 每轮 review 明确范围，将发现、处置和回归证据沉淀到有关能力。
4. 代码、规范和资料的变更完成影响判断，依据适用范围重新确认当前证据。

首期完成条件是五个试点主题可用于真实任务和 review，并建立最小格式及检查。全量覆盖需要后续持续盘点；“没有条目”表示未盘点，不能推断不支持。

本次范围不包含产品功能扩展、语言变更、Rougamo 迁移、包发布、网站托管、向量数据库或新的知识库服务。工作使用现有 checkout，保留其他未跟踪文件；不修改相邻仓库。

## 2. 正式依据与冲突治理

### 2.1 资料地位

| 资料 | 职责 | 效力 |
| --- | --- | --- |
| 正式语言规范及被明确委托的专题条款 | 定义产品契约 | 在批准的版本和范围内有效 |
| 本设计 | 定义文档、审查与同步流程 | 为后续实施基线，不代替产品规范 |
| 知识库能力条目 | 组织、解释契约及证据 | 不独立批准新的匹配语义 |
| 用户指南 | 按任务解释使用方式 | 行为陈述可追溯到能力和规范 |
| 验证报告 | 证明指定代码状态和场景的结果 | 不证明未覆盖输入 |
| 历史讨论、review、Memorix | 保存背景及检索线索 | 建议不自动具有规范效力；明确裁决需登记出处 |

规范效力由批准状态、适用版本和范围、委托关系、显式 supersedes 关系共同确定。不设“正文高于附录”的文件级排序，也不按日期自动择新。

资料逐文件、必要时逐条款登记。不能将 docs/language/ 全部认定为规范；其中的指南和历史比较需要单独标注。

### 2.2 登记与裁决

在 `docs/knowledge/sources.json` 登记来源；在 `docs/knowledge/conflicts.md` 登记实际冲突。冲突记录包含编号、相冲突条款、范围、受影响能力、阻塞判断、维护者及裁决出处。

没有明确取代关系的实际矛盾进入待裁决，不单方择一。暂停受影响的新承诺，不阻塞无关变更，不擅自改变现有实现。裁决完成后同时更新当前来源关系、有关能力和用户说明，保留原始出处。

本设计的流程决定使用 DOC-D01 等编号。产品语义裁决另行登记，不因通过文档 CI 或模型投票自动生效。

## 3. 内容结构与阅读路由

以下为实施目标路径；当前设计阶段不提前创建全部资料。

```text
docs/
  usage/
    index.md
    quick-start.md
    adapters.md
    matching.md
    results-and-diagnostics.md
    limits-and-pitfalls.md
    migration.md
  knowledge/
    index.md
    sources.json
    coverage.json
    conflicts.md
    profiles.json
    categories/<category>/index.md
    capabilities/<category>/<capability-id>.md
    review/index.md
  reviews/
    findings/<finding-id>.md
    evidence/<evidence-id>.json
    <date>-<review-scope>.md
eng/
  verify-documentation.ps1
.github/
  PULL_REQUEST_TEMPLATE.md
```

### 3.1 渐进式披露

- 总入口说明项目范围、规范来源、状态含义、目录和任务路由，不复制条目正文。
- 分类页列出能力摘要、关键边界、未盘点主题及关联入口。
- 能力详情先呈现短摘要，再提供契约、输入条件、阶段结果、例子、实现和证据。
- 只有受任务影响的能力及关联契约需要进一步加载。历史讨论不进入默认阅读路径。
- 支持矩阵后期从条目生成；首期分类摘要可手工维护，但状态含义必须一致，不另建第二份权威状态数据。

现有 README 保持简短入口，连接用户指南和正式规范。现有 docs/language 文档按来源地位保留、修订或建立链接，不复制全部语法定义。

### 3.2 用户文档

用户指南覆盖安装与适配器选择、快速开始、类型/成员/属性/泛型匹配、逻辑与 regex、结果和诊断、生命周期、限制、迁移。已接受且仍存在的缺陷或风险需要让受影响用户可见。

每章声明能力编号集合；支持、限制、诊断等行为性陈述能追溯到对应条目，叙述不逐句挂编号。指南按用户任务拆分，不以“五个主题必须五个文件”验收。

新解释性资料使用中文；API、DSL、诊断码和符号保持原名。既有英文正式规范继续为权威文本，不维护另一套竞争性规范译文。知识库入口维护中英术语表。

### 3.3 分类与稳定编号

| category 值 | 内容 | 能力前缀 |
| --- | --- | --- |
| types | 类型名称、嵌套、程序集身份、类型转发与结构身份 | TYPE |
| generics | arity、声明身份、闭合上下文、约束、变量、variance | GEN |
| type-uses | 数组、nullable、tuple、ref-kind、指针、函数指针及 custom modifier | USE |
| members | 方法、构造、访问器、事件、运算符、显式接口及生成成员 | MEM |
| csharp-metadata | async、iterator、partial、源码与 PE 表示 | CSH |
| attributes | 直接记录、目标、编译器标记与读取条件 | ATTR |
| syntax | 词法、邻接、语法、转义、恢复及解析诊断 | SYN |
| semantics | 绑定、selector、模式作用域、匹配与关系语义 | SEM |
| cross-cutting | 可用性、三态、诊断、取消、限制、缓存、生命周期、API、包及格式化 | CROSS |

能力编号格式为 `<前缀>-<稳定主题名>-<至少三位序号>`，例如 USE-REF-001、CROSS-LOGIC-001。主题由大写字母、数字和连字符组成；编号全局唯一，分配后不复用。

前缀代表稳定语义族，目录位置不参与校验。条目移动不改编号；改变语义族或拆分条目时分配新编号，保留旧编号的重定向及取代说明。一个条目只有一个主要分类，可被多个索引引用。

regex 的扫描和语法子集归 SYN；运行时匹配和结果归 SEM；规范签名文本归独立 CROSS 格式化契约，并关联前两者。阶段诊断按具体契约分类，不仅根据规范章节号判断。

## 4. 能力条目与状态

### 4.1 粒度

一项能力是可独立承诺、独立证伪的契约单元。DSL、模型、核心和适配器是条目内维度，不机械拆成多份相同契约。不同输入或后端有不同承诺时，用条目内的场景记录。

每个场景必须描述适配器、入口/输入模式、事实条件、目标版本和预期行为。状态在场景层记录，条目摘要由场景派生，避免某一后端已验证就将整个能力标绿。

### 4.2 状态枚举

| 字段 | 取值 | 含义 |
| --- | --- | --- |
| contract_status | supported / excluded / pending | 承诺支持、明确排除、待裁决 |
| verification_status | unverified / verified / needs_reverification / failed | 未验证、已验证、待重验、验证失败 |
| verification_methods | automated / manual 的集合 | 可登记验证路线；有执行证据才表示已完成验证 |

实现缺陷不改写承诺。环境失败不能自动证明产品违约；运行结果需注明归因。

场景初始为 unverified；有覆盖所声明预期行为的适用通过证据，才改为 verified。有关变化使旧证据适用性未定时改为 needs_reverification；确认可复现的产品违约时改为 failed。归因未明的失败或环境中断不自动标 failed，初次验证未完成仍为 unverified，曾有有效验证而当前无法确认时为 needs_reverification。修复后根据新的适用证据恢复 verified，不仅因 Finding 关闭而恢复。同一场景未解决的当前反例不能被其他通过报告抵消。

excluded 场景必须有原因、批准依据及失败表现。原因采用 out_of_scope、dsl_not_expressible、explicit_exclusion、backend_or_version_limit、resource_limit 五类。单次元数据不足不是静态排除原因。

未验证事项写明具体缺口及是否影响对外承诺。源代码中存在测试只表示证据入口已经找到，不等于测试已运行通过。

### 4.3 阶段与输入边界

条目分别记录解析/绑定、原生映射、匹配、调用方转换的结果或失败方式。输入条件影响当次处理的结果、诊断或异常，不直接改写静态契约状态。

现有契约中，原生映射超限抛 AspectNLimitException，而匹配手构超限中立签名返回 Unknown；取消按相应入口传播，不能统一转换为 Unknown。无原生关联、读取失败、无效参数和合法但不支持的形态也需要分别描述。

“人工构造”不是“无效”的同义词。输入类别、生产者约束、入口可达性和所指契约必须明确。

### 4.4 模板

使用单一 Markdown 模板和一个 JSON 元数据块，格式见配套材料。JSON 是机器字段的唯一权威来源；正文摘要解释其结论。

| 内容 | feature 条目 | cross_cutting 条目 |
| --- | --- | --- |
| 编号、标题、分类、场景状态、规范依据 | 必填 | 必填 |
| 摘要、契约/不变量、输入及适用范围 | 必填 | 必填 |
| 阶段结果和失败表现 | 必填；无有关阶段写理由 | 必填；按入口和阶段说明 |
| DSL/模型/核心/适配器维度 | 必填；无关维度可声明 N/A | 仅适用维度必填，其他引用 profile 理由 |
| 正例、边界或反例证据 | 必填 | 可用真值表、性质、诊断或生命周期场景 |
| 实现入口、证据入口、关联关系 | 必填；无关联使用空集合 | 同左 |
| 不支持原因 | excluded 场景必填 | 同左 |
| 未验证事项 | 非 verified 场景必填 | 同左 |

profile 在 profiles.json 中定义适用不变量及条件，条目可以继承同类条件，但仍登记自己的适用结论。一个性质没有合法反例时，用边界或性质证据说明，不能制造错误的 NotMatched 预期。

## 5. 证据、覆盖与当前有效性

### 5.1 证据报告

证据编号采用 EV-YYYYMMDD-NNN。报告记录方法、场景、独立预期来源、命令或人工步骤、结果、时间、环境、实际代码状态及依赖范围。

实际代码状态包括 HEAD 和有关文件的 SHA256；dirty 状态不能仅以 HEAD 标识。环境按需要包含 TFM、运行时、编译器、依赖版本及源码/PE 模式。原始日志可以保存在 artifacts/，正式报告进入版本控制并提供重生成方式。

预期依据区分正式规范、独立元数据核对、仅跨适配器一致性。仅一致性和仅测试源码检查不能独立证明全部契约。

报告结果采用 passed、failed、inconclusive；源码检查属于有限的人工取证，不能据此把运行行为标 verified。不可重复的一次性核对需要保存步骤、输入摘要和重验证触发条件。

### 5.2 有效性与派生显示

历史报告保持原代码状态和结论。代码或规范变化触发当前适用性评估，不重写旧报告，不因整个提交 SHA 改变就作废所有证据。

变化涉及实现、测试、规范条款、构建配置或依赖环境时，评估对应场景是否待重验。影响声明是首期主入口，review 补充漏报；文件哈希只检测声明范围的变化，不保证依赖模型完整。

证据报告、支持矩阵和状态字段本身不进入被验证输入，避免验证状态更新导致自身失效。自动依赖和缓存建模后置。

已验证表示指定版本、场景和范围有适用证据。支持视图同时显示承诺、验证范围、确认缺陷和仍存在的已接受风险，不以“支持*”代替具体说明。Finding 已关闭为不修复，不表示对应风险已经消失。

### 5.3 覆盖盘点

coverage.json 记录规范条款、公共 API、适配器事实、候选 .NET/C# 主题及历史确认发现的盘点状态。

盘点编号采用 INV-NNNN；状态为 unassessed、documented、needs_evidence、reviewed。未建档可无能力编号；建档后关联有关条目。reviewed 只表示登记范围已审查，不表示所有版本、后端和组合已穷举。

覆盖统计分别显示已盘点范围、证据覆盖和已审查范围，不能用条目数量或测试数量替代能力完整性。

## 6. Code Review 与 Finding

### 6.1 范围和不变量

每轮正式记录确定代码状态、能力、输入模式、环境、适用不变量、所选交叉场景及排除范围。组合以历史种子和影响分析选择，不要求全组合穷举。

- 三态传播仅适用于相关求值契约。
- 跨适配器一致性要求等价输入及同样可用的所需事实；差异有独立依据。
- 缺失元数据场景仅要求于消费元数据的能力。
- 取消检查验证有关入口的可观察行为，不规定逐条插入实现检查点。
- 资源阈值遵循已批准产品契约，测试中的时间或分配阈值不自动成为产品保证。

N/A 结构化记录不变量编号、适用条件引用、理由、核验状态、核验人及日期。

### 6.2 N/A 核验，落实原 D4

试点期，新增、改动或因 profile 改变而受影响的 N/A 默认 pending，全部人工核验后方可用于通过结论。核验由非条目作者的维护者或审查者承担；reviewer 为实际核验者，签章是姓名/Agent 标识与日期，不要求密码学签名。

每轮对范围内既有且适用条件未变的已核验 N/A，以“能力编号 + 不变量编号”的独立记录为分母，抽查至少 ceil(N/3)。N 为零时无需抽查；已全量核验的新增/改动记录不重复计入。范围记录列明候选、抽中和结果，轮转抽样避免长期只检查同一部分。

规模化准备闸门通过后，采用结构化 lint 加触及条目抽查。适用条件变化和实际不一致仍需重新核验。

### 6.3 Finding 格式和阻塞通道

Finding 编号采用 FND-YYYYMMDD-NNN，记录分类、能力或盘点关联、原始复现/明确路径、登记状态、预期、实际、反证尝试、影响和处置。

分类采用 defect、contract_gap、evidence_gap、robustness_risk、improvement。输入类别、阻塞通道、严重度、可信度、阻塞决定五个字段独立。严重度为 high、medium、low、unrated；可信度为 confirmed、limited、unverified；通道为 contract、robustness、none；阻塞决定为 pending、yes、no。

两条通道落实原 D2：

1. contract：承诺输入与入口上确认、可复现的实质违约，对该变更或发布有实质影响。匹配状态、错误 Unknown、承诺诊断/异常和资源行为属于可观察契约；非契约文案或内部开销不能直接升级。
2. robustness：真实交付公共入口或可证明生产链上，同时有可达性、可复现和严重危害证据，由维护者裁决。普通已批准异常及调用方未捕获异常不直接证明不可恢复的进程危害。

承诺范围内的手工输入可走 contract；绕过生产者约束的损坏对象默认不阻塞，不外推真实程序集。证明“调用了同一方法”不足以证明原缺陷必要条件在合法路径成立。

纯内部优化可以无能力编号，但需要影响判断；触及公开相等性、线程安全、生命周期、诊断或限制时关联相应契约。

### 6.4 生命周期与关闭

| status | 含义 | 所需证据 |
| --- | --- | --- |
| open | 已登记且在分析/修复中 | 原始事实及影响 |
| pending_evidence | 证据不足 | 缺口及阻塞判断，不假定不成立 |
| pending_decision | 等待维护者裁决 | 冲突/风险及所需决定 |
| fixed | 已修复 | 原复现或等价映射在关闭状态符合契约，附回归 |
| rejected | 不成立/撤销 | 反证、错误前提及出处 |
| accepted_risk | 已接受风险/不修复 | 明确裁决、范围及重新评估条件 |
| documentation_resolved | 文档或契约问题已处理 | 修订和冲突解决证据 |

fixed 尽量保留旧红新绿；其余终态按自身证据关闭。未知事实不能直接标 fixed 或 rejected。已批准不修复没有新证据或范围变化时不反复重开；行为再次违反已修复承诺时可同号重开。

正式记录跟踪入仓。未跟踪原始报告不能独立替代正式裁决，但可通过可重现步骤和正式记录引用作为辅助证据。

## 7. 同步规则与首批检查

### 7.1 变更影响

公共 API、DSL、匹配语义、适配器、诊断、限制或兼容性变化，声明能力编号、场景、是否改变契约、所需资料和证据。无用户可见影响时记录具体 N/A 理由。

允许同一可审查变更中多次提交。以最终状态是否有适用证据评估，不要求最终元数据必然停留在待重验。维护者接受残余风险时记录理由，不宣称其已验证。

未盘点只暂缓能力编号要求，仍遵守现有规范和 conformance 同步规则，并新增盘点记录。未裁决未来行为不写成当前稳定功能。

AGENTS.md 首期加入发现性路由；完整规则在准备闸门通过后与既有语言同步句合并，不建立两套重复规则。规范冲突不得通过仅修改用户说明来合理化实现缺陷。

### 7.2 格式与校验

采用 PowerShell 7 和系统 JSON 能力实现 eng/verify-documentation.ps1，使用 `pwsh -NoProfile -File eng/verify-documentation.ps1`。不新增第三方解析依赖，不要求文档检查启动 dotnet 测试。

校验仅覆盖登记的来源和新资料格式，不要求历史讨论符合新模板。复用现有 ci.yml，文档校验为其中一项检查，不创建独立 workflow。

首批硬错误：JSON/版本格式、编号唯一和前缀映射、枚举和条件必填、能力/规范引用、本地文档链接及用户章节能力引用。

首批告警，落实原 D3：open_findings、related_findings 等 Finding 引用缺失或所指记录不存在，或 open_findings 指向已经关闭的记录；新结构尚未迁入的历史发现给出迁移提示，不机械阻塞试点。已接受但仍存在的风险通过 related_findings 保留，不能因不在 open_findings 而隐藏。

外部网站链接不联网检查；符号存在性、示例编译、矩阵生成、自动证据适用性判断后置。CI 不证明语义、N/A 理由、审批真实性或能力盘点完整性。

PR 模板记录影响能力、场景、同步清单、证据与不适用理由。纯文档变更按所需检查验证，不自动重跑整个产品测试矩阵。

## 8. 实施阶段与准备闸门

| 阶段 | 交付物 | 验收 |
| --- | --- | --- |
| A：资料盘点与格式 | sources、coverage、冲突记录、profiles 与最小模板 | 规范范围明确；历史资料不误作当前契约 |
| B：五主题试点 | 泛型身份、ref 分类、数组形状、可用性、三态条目及用户任务章节；AGENTS 路由 | 有功能和横向样例；每主题至少一个可验证用户示例 |
| C：实际审查 | 非作者按入口完成任务、影响分析和一次 review | 发现可追溯；N/A 核验完成；已知与未知范围能被识别 |
| D：首批校验与同步 | 轻量 CI、PR 模板、Finding 引用告警 | 正常记录可通过，结构错误可识别；不误阻塞历史迁移 |
| E：扩展与生成 | 其余分类、支持矩阵、必要示例执行 | 扩展范围经盘点；生成数据无第二权威副本 |

完整同步规则的生效闸门：试点通过；字段与 profiles 可用；当前需治理的变更范围已建档或有盘点例外路径；引用检查及 PR 模板可用；维护者明确确认生效范围。阶段编号和条目数量本身不触发全仓强阻断。

试点记录编写/更新/核验耗时、定位依据的路径、重复提出已裁决发现的情况和漏报能力。指标用于调整成本，不设未验证的硬耗时门槛，也不将“发现数量变少”单独视为正确性提高。
