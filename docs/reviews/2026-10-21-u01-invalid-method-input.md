# U01 损坏方法签名的输入边界裁决

## 维护者裁决与适用范围

2026-10-21 维护者明确：“对于这种已损坏的包应该直接拒绝映射，不应该为这种本身就有问题的程序集提供兼容，AspectN 是用来处理正常程序集的”。随后授权核对是否需要代码、测试或文档变更，并直接执行必要变更。

据此确定 U01 的处置：必要方法签名损坏、无法读取时，映射失败并保留异常；不为继续匹配而修补签名、返回不完整的 `MethodSignature`，也不将这种失败转换为 Unknown/Unsupported。拒绝新增损坏程序集容错的建议，不作为合并阻塞项。合法的 void 返回同样具有返回类型，不能与缺少 ReturnType 混淆。

本裁决确定输入范围，不要求增加全程序集完整性预检、不保证主动发现每一种损坏，也不要求统一所有损坏形式的异常类型、文案或精确抛出位置。正常程序集缺依赖、原生候选无法加载、独立元数据事实不可用，各自仍按现有加载和可用性契约处理。U01 不改变 D01 已批准的合法结构超限通道。

## 代码与测试结论

核查基线 `f298b55912957c9544dd40ac51e1bd566315689e`，分支 `codex/aspectn-redesign-spec`：

- `CecilSignatureMapper.MapMethod` 直接执行 `CecilNativeTypeLimitGuard.ValidateMethod`，随后建立缓存键及调用 `MapMethodCore`，没有将必要签名读取失败整体改写为不完整方法签名的 catch。
- 限制检查遍历声明类型、返回类型及各参数类型；`MapMethodCore` 还需要这些结构才能建立中立签名。必要结构读取失败的异常可向调用方传播。因此 U01 不需要增加代码，也不添加恢复分支。
- `MapProperty` 的局部保护针对属性参数集合，`MapPropertyCore` 将独立事实标记为不可用。这不等同于方法必要形状缺失，不能仅据 catch 不对称推导出必须修改 `MapMethod`。
- 既有 `CecilUnavailableMetadataTests.MapProperty_DamagedLazySemantics_PreservesIndependentFacts` 是修改内部表信息后核对独立事实的底层回归；保留测试和已有恢复路径，不将其外推为损坏程序集兼容保证。

本轮不新增或修改生产代码及测试。没有新的产品行为需要回归，也不为任意人工损坏对象固化某个具体异常类型。仅有源代码核查不能替代真实 DLL 执行；本轮未执行损坏 PE 探针，未重跑 H1，也不复用上一轮完整矩阵声称 U01 已验证。

## 历史问题与当前处置

综合报告 U01 来源于 GLM-I2：从 `MapMethod`/`MapProperty` 的 catch 不对称推断第三方损坏 DLL 会导致扫描进程崩溃。原报告没有真实 DLL 或有效生产链复现，这一后果仍未验证。

本轮拒绝的是“必须为损坏方法签名增加容错”的建议，并未证明此类输入不会抛异常，也没有把 U01 标记为已修复的产品缺陷。FND-20261021-006 以 improvement/rejected 登记本次决定；旧 H1 的 accepted_risk 及证据缺口保留，原综合报告、旧 Finding 和历史证据均不改写。新的真实 DLL 证据可用于判断输入是否实际正常、或是否涉及已承诺的独立事实恢复，不自动触发对损坏签名增加兼容。
